# ADR-0003: パネルは NSPopover ではなく、アクティブ化しない NSPanel に載せる

## Context

パネルにはポップアップボタン（インターフェース、表示、単位）がある。初版は RFP §3 のとおり
`NSPopover` に載せ、表示直後に `makeKey()` していた。

`makeKey()` はポップオーバーを key にするが、アクセサリアプリ自体は非アクティブのままである。
そのためパネル内の最初のクリックがアプリをアクティブ化し、その通知が、いま開いたばかりの
メニューの追跡中に届いて追跡を終わらせる（実測: メニュー開始の 78 ms 後に終了）。

初版ではこれを「パネルを開くときにアプリをアクティブ化する」ことで塞いだ。端末から起動した
デバッグ版では 9 回中 9 回、表示の 12〜39 ms 後にアクティブ化が完了し、問題は消えたように見えた。

リリース後、署名済みバンドルを LaunchServices 経由で起動して測り直すと、**起動直後の最初の 1 回は
アクティブ化の要求が通らなかった**。要求の後も最前面は直前のアプリのままで、`didBecomeActive` は
来ず、最初のクリックで初めてアクティブ化が起きてメニューが 71 ms で終了した（1 回、再現）。
macOS 14 以降のフォーカス奪取防止は、起動直後のアクティブ化を最大で約 30 秒拒否する — 組織の
ナレッジに記録済みの事実で、採用時に引き当てていなかった。macOS 27 ではステータス項目への
クリックを別プロセスが受け取るため、OS から見ればこの要求は利用者の操作に紐づいていない。
端末から起動した版で通っていたのは、最前面アプリの子プロセスだったためと考えられる。

## Decision

1. パネルは **`.nonactivatingPanel` を持つ `NSPanel`** に載せる。パネル内のクリックはアプリを
   アクティブ化しないので、メニューの追跡を中断するものが無くなる。アプリは一度もアクティブ化を
   要求しない。
2. それに伴い、初版にあった「開くときにアクティブ化し、閉じるときに直前のアプリへ返す」処理は
   取り除く。奪わないものは返す必要が無い。
3. パネルは key になれる（`canBecomeKey`）が main にはならない。`hidesOnDeactivate` は使わない。
   表示はアニメーションなしで、開閉の状態は自前の真偽値で持つ（ウィンドウの `isVisible` に頼らない）。
4. 位置はステータス項目の直下・中央揃えで、画面の表示領域に収める。位置の計算は純関数にする。
   項目の幅やパネルの高さが変わったら置き直す。
5. 素材は常にアクティブ状態で描く。アプリが非アクティブのままなので、ウィンドウの状態に追従させると
   沈んだ色になる。
6. 閉じる経路は 1 本にする。外側クリック（global + local モニタ）、項目の再クリック、Esc の
   すべてがそこを通り、モニタの解除と内容の破棄を必ず行う。
7. 内容は開いたときに生成して閉じたら破棄する、メニュー追跡中は更新を保留する、項目クリックと
   action を順番で対応付ける — これらは載せ替えの前後で変わらない。

## Consequences

- 起動直後でも、最初のクリックからメニューが使える。他のアプリからフォーカスを奪わなくなる。
- ポップオーバーの吹き出し（矢印）は無くなる。項目の直下に置くことで対応関係を示す。
- 表示位置・寸法・素材を自前で持つことになる。ポップオーバーが暗黙に面倒を見ていた部分である。
- キーボードのコピー（⌘C）はメインメニューが無いので効かない。これは初版と同じで、アドレスと
  版数の選択とコンテキストメニューからのコピーは使える。

## Alternatives considered

- **`NSPopover` のまま、開くときにアクティブ化する**（初版）。不採用。起動直後は要求が拒否され、
  拒否されたときに打てる手が無い。通る場合でも他のアプリからフォーカスを奪い、返す処理が要る。
- **起動時に一度アクティブ化しておく。** 不採用。ログイン時起動で利用者の作業中のアプリから
  フォーカスを奪う。拒否される時間帯がまさに起動直後である。
- **最初のメニューが途中で閉じたら開き直す。** 不採用。利用者のクリックを合成イベントで再現する
  ことになり、原因ではなく症状を相手にしている。
- **ポップアップボタンをやめ、セグメントやラジオボタンにする。** 不採用。インターフェースの一覧は
  件数が不定で、メニュー以外に収まらない。

## Amendments

### 2026-09-20 — リリース前の独立検証の指摘による追補

- **「フォーカスを奪わなくなる」は不正確だった。** アプリが取らないのは**アクティブ化**で、
  最前面のアプリは変わらない（実測）。パネルは開いている間 key を取るので、その間のキー入力は
  パネルに届く — Esc が効くのはそのためである。README と CHANGELOG はこの言い方にした。
- **決定 6 は閉じる経路を 3 つ挙げたが、5 つある。** よそへ行く操作はマウスダウンを伴うとは
  限らない: 別のアプリが最前面になる（⌘Tab）、Space が切り替わる。ポップオーバーはこのとき
  自分で閉じたが、アクティブ化しないパネルには何も通知されず、Space 切替の後は見えない場所で
  開いたままになり、次の項目クリックが誰にも見えないパネルを閉じていた。どちらも同じ経路で閉じる。
- **「モニタの解除を必ず行う」は言い過ぎだった。** 閉じる経路はモニタを状態に合わせる。
  項目への閉じるクリックの action を処理し終えるまでは、モニタは残る。
- **既知の制限（未対応）:** 画面の表示領域より背の高い内容（表示領域の高さが約 566 pt 未満）は
  上下が切れる。スクロールする設計が要る。
- **新しいパネルで未実測:** コンテキストメニューからのアドレスのコピー。

### 2026-09-21 — 器は ADR-0004 で置き換え

パネルを開いている間、項目が他のメニューバー項目のように押された見た目にならないことに利用者が気づいた。
macOS 27.0 での実測: メニューバーがこのハイライトを保つのは `NSPopover` と `MenuBarExtra` だけで、非公開の
仕組みによる。自前のパネルに点ける公開 API は無い。パネルは `MenuBarExtra` の窓に移した。この決定の理由は
`NSPopover` については今も成り立つ — 実験で、起動直後の最初のクリックがメニューを 88〜97 ms で終わらせる
ことを再現した（2 回中 2 回）— が、`MenuBarExtra` では同じメニューが開いたままだった（3 回中 3 回）。
決定 1・3・4・5・6 は置き換え、決定 2（アプリはアクティブ化を要求しない）は引き続き有効。決定 7 のうち、
中身は一度作って保持し開いている間だけ更新する形に変わり、更新の保留は残り、クリックと action の突き合わせは
窓とともに無くなった。⌘C についての結果はもう成り立たない: SwiftUI のライフサイクルが標準メニューを入れ、
パネルから ⌘C でコピーできる（手での確認）。
