# ADR-0001: カウンタの読み取りを速度に変える規則 — 差分・破棄・リセット判定

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-09-20 |
| Binds | net-meter |
| Decision makers | nlink-jp maintainers |
| Triggered by | RFP が「Phase 1 で実測して決める」とした、巻き戻りとリセットの区別。追補 A2〜A4 |

## Context

net-meter は 1 秒ごとに IF 別の累積カウンタを読み、前回との差から速度を出す。
差が信用できない場合にそれを速度として表示すると、数 GB/s の棘になる。どの差を信用し、
どれを捨てるかを、実測に基づいて決める必要がある。

実測で分かっていること（計測コードと再現手順は `spikes/README.md`）:

| 事実 | 環境と回数 |
|------|------------|
| バイトカウンタは、真値を 2^32 で割った余りを 1 KiB 単位に切り捨てた値で渡される | macOS 27.0 実機・有線で 3 回、macOS 26.6.2 の VM で 1 回。いずれも `netstat` で前後を挟み、真のカウンタが 2^32 を超えた状態で確認 |
| パケット数カウンタは加工されていない（切り捨てなし、`netstat` と一致） | macOS 27.0 で 2 IF、macOS 26.6.2 で 1 IF、各 1〜2 回。32bit に切り詰められるかは未確認（2^32 パケットに達した IF が無い） |
| リンク速度として読める値は、実際の上限ではない | ホストの仮想 NIC は 100 Mbps と報告しながら 2.3 Gbps を運んだ。VM 側の仮想 NIC は 0 を報告した。有線は 2.5 Gbps（`ifconfig` の表示と一致）、Wi-Fi は約 239 Mbps |
| 1 サンプルの「バイト数 ÷ パケット数」には物理的な上限がある | 286 MB/s の負荷を含む 50 サンプル・17 IF で最大 31,477。TSO により 1 パケットは MTU より大きくなるが、64 KiB を超えなかった |
| パケットが 0 個なのにバイトだけ 1 KiB を超えて増えたサンプル | 同じ 50 サンプルで 0 件 |

まだ測っていないこと: スリープ復帰がカウンタに何をするか。VPN のトンネル IF が作り直されるとき。
アダプタの抜き差し。これらは Phase 1 の残りの実機確認で測る。下の規則は、その結果によらず
安全側に倒れるように作る。

## Decision

IF ごとに、前回の読み取り P と今回の読み取り C、その間の経過時間 dt から、次の順で 1 つの結果を決める。
経過時間はスリープ中も進む時計（`ContinuousClock`）で測る。

1. **P が無い** → `baseline`。C を基準として覚え、速度は出さない。IF が読み取りから消えたら、
   その IF の基準は捨てる。再び現れたときは必ずここから始まる。トンネル IF の作り直しや
   アダプタの抜き差しは、まずこの経路で処理される。
2. **dt < 0.5 秒** → `tooSoon`。何も出さず、基準は P のまま据え置く。タイマーが詰まった後に
   2 回続けて発火すると、極端に短い間隔で割ることになる。
3. **dt > 3 秒** → `discarded(intervalTooLong)`。C を新しい基準にする。値は見ない。
4. バイトとパケットの差分を、どちらも **2^32 を法として**取る。
5. **どちらかの方向のパケット差分が 2^26 × dt を超える** → `discarded(reset)`。C を新しい基準にする。
   後退したカウンタは、2^32 を法とした差分では巨大な前進として現れる。
6. **どちらかの方向で、バイト差分 > (パケット差分 + 16) × 131,072 + 1,024** →
   `discarded(reset)`。C を新しい基準にする。
7. それ以外 → `rate`。速度は差分 ÷ dt。累積転送量にはこの差分だけを足す。

定数の根拠:

- **3 秒**: 1 回の取りこぼしと揺らぎを許す。この間隔でも 10GbE の全力（3.75 GB）は 2^32 バイトに
  収まる。1 秒間隔なら約 34 Gbps、3 秒まで延びた間隔では約 11 Gbps までが一意に決まる。
- **2^26 パケット/秒**（約 6,700 万）: 10GbE の最小フレームでの上限（約 1,490 万）の 4 倍強。
- **131,072 バイト/パケット**: 実測の最大（31,477）と IP パケットの上限（65,535）に対して 2 倍の余裕。
- **+16 パケット、+1,024 バイト**: バイトとパケットのカウンタが同時に更新されないことへの余裕と、
  1 KiB 切り捨てのぶん。

破棄されたサンプルと `baseline`・`tooSoon` は、速度 0 ではなく「値が無い」状態として表示層に渡す。

## Consequences

- スリープ復帰は、カウンタが実際にどうなるかによらず規則 3 で再基準化される。
- リセットを見逃す場合が残る。リセット直前のパケット数（2^32 を法とした値）が上端から
  2^26 × dt 以内にあると、規則 5 をすり抜ける。その値が一様に分布すると仮定しても、1 秒間隔で
  1 方向あたり約 1.6%、両方向が同時にそうなるのは約 0.02% で、そのうえで規則 6 も通る必要がある。
  実際のパケット数は 2^32 よりずっと小さいことが多く、確率はさらに低い。見逃した場合の症状は、
  1 サンプルだけの棘である。
- 34 Gbps を超える実通信は、1 秒間隔では正しく測れない。リンク速度からこれを検出して
  サンプルを捨てることはしない — 申告されるリンク速度が当てにならないうえ、実通信がその域に
  達しないかぎり値は正しいので、捨てるほうが損失になる。
- 1 KiB の切り捨てのため、1 KB/s 未満の通信は 0 と 1 単位のあいだを行き来する。
  表示側で均すかどうかは、この ADR の範囲外とする。
- 規則は `NetMeterCore` の純関数として実装し、実測で得た値の並びをそのままテストの入力に使う。

## Alternatives considered

- **リンク速度 × 経過時間を上限にする**（RFP の当初の候補）。不採用。実測で、申告値が実際の
  上限でない例（100 Mbps と申告して 2.3 Gbps）と、0 を申告する例を得た。正しいサンプルを捨て、
  かつ 10GbE ではリセット後の差分の約 3 割を通す。
- **カウンタが前回より小さければリセットとみなす**。不採用。バイトカウンタは 4 GiB ごとに
  正常に巻き戻るので、後退と巻き戻りを値だけでは区別できない。
- **フィールドが 64bit であることを信じ、巻き戻りを扱わない**。不採用。macOS 26 と 27 の両方で
  32bit への切り詰めを実測した。
- **スリープ中に止まる時計で経過時間を測る**。不採用。スリープが普通の長さの間隔の中に隠れ、
  規則 3 が働かない。
- **`ifi_lastchange` などの状態変化時刻を使う**。見送り。リンク状態の変化は示すが、
  カウンタのリセットを示す保証が無く、未実測。
- **非公開の NetworkStatistics を使う**。不採用。RFP のスコープ外（非公開 API）。
