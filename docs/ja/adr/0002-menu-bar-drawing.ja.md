# ADR-0002: メニューバーの描画方式 — 「値 → 画像」の純関数と 2 つの仕上げ

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-09-20 |
| Binds | net-meter |
| Decision makers | nlink-jp maintainers |
| Triggered by | RFP 追補 A5。モノクロ既定（メニューバーの明暗に追従）と色付きモードは、素朴な 1 つの描画経路を共有できない |

## Context

メニューバーには 2 行の数値とグラフを、固定幅で、毎秒描き直す。モノクロが既定で、設定により
上り/下りを色分けできる（RFP §2）。

- テンプレート画像（`isTemplate = true`）は、OS がメニューバーの明暗・壁紙の着色・押下時の
  ハイライトに合わせて塗り直す。ただし色を持てない。しかも `isTemplate` が尊重されるのは
  `NSStatusItem.button.image` に置いた画像だけで、タイトル文字列に埋め込んだ画像では効かない
  （組織ナレッジ「メニューバーのアイコンは `button.image` に入れる」）。
- テンプレートを外すと、指定した色がそのまま焼き込まれ、数値の文字色も含めて明暗に追従しなくなる。

実測（`spikes/status_appearance.swift`、macOS 27.0、1 回）: システムがライトモードで
アプリの外観が Aqua のとき、ステータス項目のボタンの `effectiveAppearance` は `VibrantDark`
だった。ボタンはシステムの明暗ではなく、**メニューバー自身の明暗**（暗い壁紙で暗くなる）を報告する。
同じ実測で、ボタンの高さは 22pt、表示倍率は 1 倍（非 Retina）だった。

## Decision

1. 描画は **「表示する値 + 仕上げ → 画像」の純関数** 1 つにまとめ、結果を `button.image` に置く。
   タイトル文字列もサブビューも使わない。
2. 仕上げは 2 つ。
   - **モノクロ（既定）**: すべてを黒（濃淡はアルファ）で描き、`isTemplate = true`。
     色は OS が決めるので、他のシステム項目と完全に揃い、押下時のハイライトも OS 任せになる。
   - **色付き**: `isTemplate = false`。数値と基線の前景色は、**ボタンの `effectiveAppearance`**
     が暗いか明るいかで選ぶ。上り/下りの色は、暗い・明るいメニューバーそれぞれに 1 組ずつ持つ。
3. 毎秒の描き直しが外観の変化も拾う。外観の変化だけのための監視は置かない。
4. 描画は実画面の表示倍率で行い、線と棒はピクセル境界に合わせる。1 倍表示が実在する。
5. 幅は値に依存しない。数値欄は `RateFormatter.numberWidth` 文字ぶん、単位欄は最長の単位ぶんを
   常に確保し、表示モード（数値+グラフ / 数値のみ / グラフのみ）だけが幅を変える。
6. 値が無い状態（不在、計測開始直後、破棄されたサンプル）も同じ関数が描く。不在は全体を淡くし、
   0 KB/s と見分けられるようにする。

## Consequences

- 色付きモードの数値の色は、OS がテンプレートに与える色と完全には一致しない。色付きは利用者が
  選んで入るモードなので受け入れる。既定のモノクロには影響しない。
- 描画が純関数なので、明暗 × 倍率 × 表示モード × 状態の組み合わせを、アプリを起動せずに
  オフスクリーンで検査できる: 幅が値で変わらないこと、モノクロでは色が出ないこと、
  上りが中央より上・下りが下に描かれること。
- 外観の切替から表示への反映は最大 1 秒遅れる。
- 「ボタンがメニューバーの明暗を報告する」は 1 回の観測に基づく。明るいメニューバーでの確認と、
  色付きモードの配色は、Phase 2 の実機調整で詰める。

## Alternatives considered

- **タイトルの attributed string に色付き画像を埋め込む**（status-lens の方式）。不採用。
  2 行の固定レイアウトとグラフを文字列の流し込みで組むのは無理があり、モノクロ既定が
  テンプレートの恩恵を受けられない。
- **ボタンに layer-backed のサブビューを載せる**（load-spinner の方式）。不採用。
  既定のモノクロまで自前で色を解決することになり、他のシステム項目と色が揃わない。
  load-spinner は固定のアクセント色を描くので、この問題が無かった。
- **モノクロ部分はテンプレート画像、色付き部分だけサブビューで重ねる**。不採用。
  2 つの描画面の位置合わせが要り、純関数 1 つで検査できる利点を失う。
- **外観の変化を KVO で監視して即時に描き直す**。見送り。毎秒の描き直しで足りる。

## Amendments

### 2026-09-20 — 表示倍率と幅（Decision 4・5 の補足）

Decision 4 は「実画面の表示倍率で描く」としたが、1 つの倍率だけで描いた画像は、Retina と
1 倍のディスプレイが混在する Mac で片方が補間されてぼける。画像に **1 倍と 2 倍の両方の
表現**を持たせ、それぞれをその倍率のピクセル境界に合わせて描く。どちらを使うかは AppKit が
画面ごとに選ぶ。混在環境での実機確認はまだ行っていない。

Decision 5 の「単位欄は最長の単位ぶん」は、**バイトとビットの両方の単位系を通じて最長**の意味で
実装する。当初の実装は選択中の単位系だけを見ており、単位を切り替えると幅が 2pt 変わっていた。

### 2026-09-21 — 画像は `MenuBarExtra` のラベルになる（Decision 1〜3、ADR-0004 を受けて）

項目は SwiftUI の `MenuBarExtra` のラベルになった（ADR-0004）。Decision 1 は結果の置き場所を変えて維持する:
1 つの関数の画像は `button.image` ではなく、ラベルの中の `Image(nsImage:)` として出す。そこでもテンプレート
画像はメニューバーに合わせて塗られる（撮影）。Decision 2 の色付き表示はボタンを読まなくなった: 明暗は
ラベルの `colorScheme` から取り、これはシステムではなくメニューバー自体の明暗に従う — `Aqua` のシステムで
`VibrantDark` のメニューバーのとき `dark`。起動直後には項目の窓が `VibrantLight` から `VibrantDark` に変わり、
48 ms 以内に追従した（macOS 27.0）。Decision 3 は実質的に維持される: ラベルは状態が変わるたび（毎秒）に
描き直され、そのたびに現在の `colorScheme` を読む。実行中のメニューバーの明暗の変化は測っていない。
